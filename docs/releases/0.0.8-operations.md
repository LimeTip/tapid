## Binary publication and recovery timeline

### Annotated-tag checkout failure

The initial tag-triggered run [`33960630649`](https://github.com/LimeTip/tapid/actions/runs/33960630649) failed while validating the annotated tag. The checkout step had materialized the local tag ref as its peeled commit, so `git cat-file -t refs/tags/v0.0.8` observed a commit rather than the remote annotated tag object.

Pull request [#121](https://github.com/LimeTip/tapid/pull/121) corrected recovery by:

- fetching the remote annotated tag object explicitly;
- validating that the ref is a tag object;
- resolving and exporting its exact peeled commit;
- requiring that commit to belong to `main`;
- checking out that exact commit before reading Cargo metadata and in every build job;
- allowing an input-free dispatch from reviewed `main` while deriving the release tag from reviewed metadata.

An early recovery proposal accepted a dispatch tag input. CodeQL correctly treated an untrusted dispatch value flowing into Git and cache selection as unsafe. The input was removed rather than sanitized into a weaker trust boundary.

### Draft read-after-write failure

Recovery run [`33970253804`](https://github.com/LimeTip/tapid/actions/runs/33970253804) built the six target archives and created draft release ID `383262465`, but the immediately following collection read did not yet return the new draft. The run failed closed before selecting an upload target.

Pull request [#122](https://github.com/LimeTip/tapid/pull/122) added a bounded release-list read-back:

- at most five collection reads;
- at most four two-second sleeps;
- exactly one matching tag required;
- the matching numeric release ID must equal the create response;
- no sleep after the final attempt.

The original draft was preserved. Successful artifacts from run `33970253804` were downloaded, checked, and uploaded to that existing numeric release ID. No duplicate release was created.

### Draft metadata recovery

During release-note synchronization, an incomplete metadata update temporarily exposed the draft under an internal `untagged-*` identity. The release was not published in that state.

Recovery preserved release ID `383262465` and all uploaded assets, confirmed that the original annotated tag remained unchanged, then restored the complete draft metadata with:

- `tag_name: v0.0.8`;
- `target_commitish: main`;
- the reviewed title and release-note body;
- `draft: true`;
- `prerelease: false`;
- latest-release promotion disabled while still a draft.

The repaired draft was read back by numeric ID and by tag before publication.

A separate attempt to set `target_commitish` to the older tagged commit returned 404 because that commit differed from the default branch in workflow files and the current OAuth grant intentionally lacked the broader `workflow` scope. No new authentication flow or broader token scope was introduced. For an existing annotated tag, `target_commitish: main` was sufficient because the tag itself provides the immutable source binding.

## Public installer evidence

Publishing triggered public-smoke run `33976229757` at exact tagged commit `35073b495b322a4619806793a204325f2867253a`.

These three jobs passed:

- `Unix installer (ubuntu-latest)`;
- `Unix installer (macos-latest)`;
- `Windows installer`.

Every job installed the explicit `v0.0.8` release and then installed through latest-release discovery. The installed binaries executed as `tapid 0.0.8`.

A later independent macOS check downloaded both public website installers, confirmed they were byte-for-byte identical to the canonical repository scripts, and repeated explicit and latest installation successfully.

## crates.io evidence

The crates.io workflow remained separate from GitHub binary publication. It waited at the protected `crates-io-release` environment until an independent reviewer approved it. Self-review prevention did not allow the dispatching actor to approve the same deployment.

The workflow used crates.io Trusted Publishing and a short-lived OIDC token. The token was revoked during post-job cleanup. No long-lived crates.io token was added.

The dependency-ordered publication completed as:

1. `tapid-archive 0.0.3`
2. `tapid-core 0.0.4`
3. `tapid-manifest 0.0.6`
4. `tapid-linker 0.0.4`
5. `tapid-lockfile 0.0.8`
6. `tapid-registry-client 0.0.4`
7. `tapid-resolver 0.0.4`
8. `tapid-store 0.0.4`
9. `tapid 0.0.8`

Independent crates.io API reads confirmed all nine exact versions as available and not yanked. A second publication dry-run returned no missing packages.

A clean installation with an isolated Cargo home and target directory completed successfully:

```sh
cargo install tapid --version 0.0.8 --locked
```

The installed binary returned `tapid 0.0.8`, and `tapid --help` succeeded.

## CI maintenance discovered during release

The release run exposed maintenance warnings unrelated to its functional failure:

- standard GitHub Actions were still on Node.js 20 based majors;
- the Windows ARM runner label had an announced Visual Studio image transition.

PR #122 updated the affected actions across all repository workflows, moved Windows ARM validation to the official Visual Studio 2026 label, added a temporary narrow `actionlint` exception because the installed catalog had not learned the new official label, and disabled persisted checkout credentials in unprivileged CI jobs.

The warning remediation was verified through repository contract tests, `actionlint`, hosted Windows ARM execution, exact-head check runs, and zero final annotations. It did not modify the immutable `v0.0.8` source tag or release bytes.

## Durable lessons

1. Source identity and workflow implementation identity are separate. Recovery may use a fixed workflow from current `main`, but it must build the exact immutable tagged commit.
2. Fetch and validate the remote annotated tag object explicitly. Do not trust the local ref shape left by a checkout action.
3. Never accept arbitrary release refs through manual-dispatch inputs when they influence checkout or cache selection.
4. GitHub release collection reads can lag successful draft creation. Retry only within a small bound and retain exact create-response ID binding.
5. Treat numeric release and asset IDs as security-relevant recovery handles.
6. Draft tag lookup and public tag lookup do not have identical visibility behavior.
7. Preserve complete metadata during draft edits and read it back immediately.
8. Do not broaden OAuth scope to perform an unnecessary target metadata edit.
9. A public release is not verified until its bytes are redownloaded and its installers execute on every supported operating-system family.
10. crates.io publication needs its own protected approval and independent registry read-back.
11. Keep the product version unified while allowing changed supporting crates to use truthful independent versions.
12. Inspect workflow warnings and annotations even when all jobs are green.
13. Prefer a concise operator runbook and focused recovery procedures over a permanent custom release state machine.

## Remaining limitations

- Release archives and their checksums share the same GitHub trust boundary.
- macOS and Windows code signing are not part of this release flow.
- Public smoke tests run after publication and therefore detect rather than prevent a broken public release.
- Self-update remains intentionally unavailable.
