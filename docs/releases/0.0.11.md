# Tapid 0.0.11 release notes

Status: unreleased. These notes describe the planned next release and its checked-in behavior. They do not establish successful public installation, upgrade, website deployment, or registry publication.

Tapid 0.0.11 makes the installers and default upgrade command use the same release record through `tapid.dev`. It also corrects upgrade output when the installed binary already matches the release or discovery uses recovery data.

## Installation and upgrades

- Discover the latest release through `https://tapid.dev/releases/v1/latest.tsv`, with explicit versions available through `vVERSION.tsv`. GitHub remains the initial archive host; clients follow archive URLs from the record without using its API.
- Validate the record, compressed archive size, SHA-256, and archive contents before staged executable replacement.
- Report an already-up-to-date result and preserve the executable when its bytes already match the verified release.
- Report that the latest release could not be checked when unavailable discovery uses last-known-good recovery. Invalid received metadata and mismatched downloads fail.
- Remove signed endpoint probes and GitHub fallback from default discovery. Explicit `--endpoint` retains the historical signed protocol. `--release-url` and `TAPID_RELEASE_RECORD_URL` select the new record protocol.
- Preserve explicit installation of historical versions through 0.0.10 using their GitHub archives and `SHA256SUMS`, unless a record override is provided. Released 0.0.10 clients can reach 0.0.11 through their existing GitHub fallback after publication.

## Release operation and verification

- Generate `tapid-release-v1.tsv` from the same six archives as `SHA256SUMS`, and publish it as the eighth asset in the existing reviewed draft.
- Keep ordinary releases independent of website redeployment. Static owned-domain routes select the provider's latest or versioned record.
- Preserve tagged installer provenance checks and separately test installation through the public website scripts.
- Add previous-version upgrade and repeated-upgrade checks on Linux, macOS, and Windows release runs. Compare resulting binaries with an independently installed latest release and require unchanged bytes on the repeated upgrade. Daily scheduled coverage is Linux only.
- Keep published validation evidence separate from reviewed source expectations. The first release requires the coordinated website cutover described in the [runbook](../release-distribution.md).

## Limits

The release record and archives share the domain and hosting trust boundary. HTTPS and SHA-256 provide transport and byte integrity, not independent release signatures, platform code signing, or provenance verification. Local rollback state does not resist hostile local modification. The new contract adds no signing keys or periodic metadata refresh requirement.

The release does not broaden native sandbox support or npm compatibility. Existing package-manager and containment limitations remain.
