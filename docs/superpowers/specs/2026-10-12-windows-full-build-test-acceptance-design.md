# Windows build/test acceptance with standard Node

## Status and requirement

The user clarified the PR [#220](https://github.com/LimeTip/tapid/pull/220) handoff requirement: use the standard Node runtime, with compatibility implemented around it by Tapid. A custom Node build, libuv backport in our own runtime, replacement binary, or waiting for a specially compatible Node release is not an implementation option. The earlier compatible-runtime requirement is superseded. The native wrapper below is a candidate requiring proof; it is not implemented or a Windows support claim.

Complete the unchanged `examples/news-site-consumer` build and default-isolation test through `tapid run` with official Node 22. Preserve declared project data/write boundaries, environment control, AppContainer authority containment and Job ownership. Network/start, missing-write-target materialization and full #157 acceptance remain separate work. Ordinary working scripts must not be rejected merely because an unrelated IPC control fails.

## Evidence and correction already made

Development evidence is from Windows 11 Home x64 build 26200, using an uncommitted worktree based on PR head `2f5746544392d3e51807169799c72e03a017adc8`. Tapid install and frozen/offline replay succeed in a disposable news fixture. Existing ordinary declared-target write and cleanup controls pass, and generated Node shebang shims now use the selected standard Node executable.

After that shim fix, Next.js build reaches EPERM obtaining metadata for C:\. Original `node --test` and minimal IPC forks hang under AppContainer with official Node 22.23.1 and 24.21.0, while inherited-stdio spawning and the same IPC payload outside AppContainer succeed. The [libuv AppContainer issue](https://github.com/libuv/libuv/issues/5178) and [fix #5181](https://github.com/libuv/libuv/pull/5181) identify the named-pipe namespace mismatch. Microsoft documents the [AppContainer LOCAL pipe namespace](https://learn.microsoft.com/en-us/windows/uwp/communication/interprocess-communication). This is a compatibility problem in our selected containment path, not a reason to change the user's runtime.

A temporary production IPC preflight was added, then removed after the user clarified this requirement. It rejected even scripts that otherwise worked and is not an acceptable substitute for compatibility. Its bounded payload remains test-only diagnostic code; it neither gates production requests nor recommends another Node build. Native and CLI positive assertions have been restored: runtime rejection does not count as successful application acceptance.

The ancestor ACL candidate also failed. Both the existing SetSecurityInfo approach and a MAXIMUM_ALLOWED-handle candidate changed descendant ACE/control metadata on deterministic legacy ACL fixtures. The candidate was removed. A read-only READ_CONTROL | WRITE_DAC probe on the real C:\ returned error 5. No shared-root ACL was changed. Keep the existing write implementation and reject unproven exact-metadata ACL mutation; do not retry this problem with broader ancestor ACLs or elevation.

## Candidate: native compatibility wrapper plus metadata broker

Keep official node.exe unchanged on disk. Tapid supplies its own separately built native compatibility component and host broker. The wrapper adapts OS calls used by Node/libuv; it does not embed V8, rebuild Node, or implement a JavaScript runtime. The selected Node identity, PATH precedence, argv, cwd, environment policy and exit behavior retain their existing contracts.

Retain AppContainer and Job as the enforcement mechanisms. API hooks provide compatibility only. Removing or bypassing a hook must not grant filesystem, network, token or process authority. The host broker independently enforces its narrow metadata capability, including against clients invoking it directly. A JavaScript preload alone is not selected: Node's internal test runner and native addons need not use monkey-patched public JS methods.

This differs from Microsoft's [Win32 app isolation](https://github.com/microsoft/win32-app-isolation), which includes platform virtualization/brokering components and currently requires app packaging. Its existence supports investigating compatibility around ordinary Win32 binaries; it is not proof that our proposed wrapper works or that packaging is an interchangeable backend.

### IPC adaptation

The first isolated prototype must address only pipe naming. Inspect the actual imports and call sites in the official Node binary. The current vendored [libuv pipe implementation](https://github.com/nodejs/node/blob/v22.23.3/deps/uv/src/win/pipe.c) generates unique names under `\\?\pipe\uv\...`; AppContainer needs the LOCAL namespace. A native compatibility shim can potentially translate that exact generated prefix to `\\?\pipe\LOCAL\uv\...` consistently at server creation and client open, without editing node.exe or its bundled libuv.

Cover both relevant ANSI and Unicode API entry points and preserve every other argument and error result. Do not rewrite arbitrary pipe names, grant host pipe access, broker arbitrary connections, or change network capabilities. This translation is a hypothesis to prove with stock Node under the actual AppContainer token, not a completed fix.

The trusted launcher must install/initialize the wrapper before the selected Node executes application code. Since the CLI starts cmd.exe, also prove propagation through the trusted shell, .cmd shims, Node children, and grandchildren. A top-level wrapper that misses test-worker processes is insufficient. Define supported architectures and mitigation-policy compatibility from native evidence; reject unsupported setup before initial project launch rather than silently running a different backend. Do not add a production injection method until its identity, initialization, cleanup and propagation contract is reviewed.

Validate two-way IPC, multiple simultaneous forks, disconnect/error paths, cross-container denial, inherited stdio, and the unchanged `node --test` command. First prototype may cover only direct Node IPC; do not label it integrated CLI or descendant compatibility until those paths pass.

### Exact ancestor metadata without host ACL mutation

Derive a finite set of canonical ancestor directories from declared project grants and verified runtime paths, deduplicated by native identity. Initially support only validated local ordinary directories. Reject unsupported reparse/alias topology and UNC/filesystem cases rather than broadening scope. Report additions with existing `ReadMetadata`, `ExactDirectory`, `BackendRuntime` types, separate from project read/write grants.

Prototype a host-side broker that opens only these pinned directories for metadata, or returns a bounded typed metadata record. It must not require WRITE_DAC, ownership changes, or administrator rights on shared ancestors. If returning handles is needed for libuv stat/realpath behavior, duplicate only the tested metadata/traversal/synchronization rights; never directory listing, file contents, writes, deletion, ownership or DACL editing. Enumerate the exact information disclosed. Keep CanonicalPath evidence unless the complete NativeObject contract is actually established.

Prefer pre-delegating a finite set of narrow metadata handles during trusted preparation if that covers the real workload. The broker can then be a preparation operation rather than a long-lived RPC service. Kernel handle rights must constrain direct native use as well as wrapper calls. Prove denial of rights escalation, root-relative escape, listing, mutation and descriptor access; an API hook is not evidence that the underlying capability is narrow. Add runtime RPC only if demonstrated behavior requires it, with the authentication and bounds below.

The native wrapper may request this capability only for qualifying ancestor metadata operations. Ordinary project file operations still use existing AppContainer ACLs. The broker validates the operation, exact pre-bound object and requested rights independently of what the wrapper says. No arbitrary paths, general filesystem RPC, child creation, or privilege-changing request is exposed.

Use an execution-specific private channel established by the trusted launcher. Bind clients and handle recipients to verified live AppContainer SID and Job membership using held native identities, not caller-supplied PID strings alone. Prove channel inheritance/distribution, bounded messages, outstanding-request limits, cancellation and closure before implementing production requests. Do not claim that a globally named pipe or an unguessable string alone authenticates clients.

The broker channel is intentional inherited authority and must be disclosed and included in handle-hygiene tests. Unrelated host handles and credentials remain excluded. If a descriptor is retained across descendants, account for that lifetime and drain the owned tree before closing resources; do not report complete cleanup on uncertainty. Broker or wrapper failure cannot cause an uncontained retry.

### Ownership, identity and packaging

Extend tapid-runner's existing Windows launcher, token verification, typed grant planning and Job cleanup. Keep CLI composition and Node selection in their existing owners. Reuse command-line/environment serialization, output capture, and verified-empty-Job cleanup. Compatibility payloads must not load project NODE_OPTIONS hooks during trusted setup.

A shipped compatibility DLL/helper needs a concrete Cargo artifact and release/install contract, immutable identity/provenance checks, architecture matching and a trusted read-only location outside project write authority. Test that a project cannot substitute the component. Receipt evidence must distinguish ACL-enforced project grants from broker-enforced metadata and disclose the extra channel and compatibility mechanism. Do not assume DLL loading or import interception is available under every Windows mitigation policy.

## Integrated component implementation after checkpoint 8cf2c84

The runner now implements the preparation-only metadata delegation and native wrapper described above. Source lives in src/windows_compatibility.rs and src/windows_compat/{dll,native,imports,protocol}.rs; build.rs compiles and embeds the target DLL. Delivery remains the signed/verified Tapid executable, with no separate installer asset and no Node runtime rebuild. Each request creates a unique component directory outside write authority, verifies embedded bytes, pins the file without write/delete sharing, and keeps the component and narrow ancestor handles alive until the existing Job lifecycle confirms no survivors. Cleanup removes only the exact owned file/directory.

The fixed bounded setup frame has explicit reserved padding, validates version/count/lengths/termination and carries only predelegated handles and finite canonical paths. There is no runtime broker service. The initial recipient's token/SID and Job are verified by the existing suspended-child implementation. Descendants inherit the kernel AppContainer/Job boundary and receive only metadata handles explicitly duplicated by their contained parent. Startup checks sensitive handle-duplication rights for every entry and root-handle reopen rights independently of API hooks. The ordinary ACL installer still rejects exact metadata mutation; these grants are delegated separately.

Native loading maps the target's actual ntdll file, completes cold-loader initialization using a trusted thread-exit entry while the application remains suspended, and resolves forwarded system functions relative to their actual target module mappings. No system-DLL address equality is assumed. Module identity uses full bounded paths, import inspection reads only committed readable image regions, original imported addresses must match system functions, and patch planning completes before changes. DllMain only records its own module. Any partial initialization leaves the image mapped and terminates the owned target; there is no resumed application or uncontained fallback. Unsupported architectures, long component paths, nonlocal/reparse ancestors, component write overlap, missing primitives and setup failure reject execution.

Checked launch evidence includes the embedded component SHA-256 and intentional non-inherited exact metadata handles. Effective grants retain CanonicalPath evidence; held objects do not silently upgrade the generic binding claim. The implementation reuses the existing request validation, command/environment serialization, ACL read/execute mechanism, native file identity, output capture, AppContainer verification and verified-empty-Job cleanup.

The Linux-hosted Windows compile-only CI lane explicitly uses TAPID_WINDOWS_COMPAT_COMPILE_ONLY=1. It type-checks the same DLL source without requiring Windows SDK import libraries, then emits an empty component marker that runtime preparation rejects. This mode is prohibited on native Windows and in release profiles. Native builds always produce the real component. This compile-only result is not runtime acceptance.

Still required for broader Windows support: native MSVC/arm64 and mitigation-policy coverage, the full authority/toolchain matrix, network-enabled start/readiness, and exact-head hosted gates. No general Windows support claim or scoped CLI permission-flag implementation is implied by this build/test integration.
