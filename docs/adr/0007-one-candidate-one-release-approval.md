# One candidate and one release approval

Tapid's 0.0.11 release required separate workflow dispatches, manually transferred release IDs, and repeated promotion approvals. We retain GitHub Actions and the existing verification helpers, but connect release preparation and publication around one exact candidate. This decision supersedes ADR 0004's manual draft publication and separate crates.io dispatch and approval requirements for the automatic release lane.

A maintainer starts the GitHub-native preparation workflow and reviews its release PR. The intent records the analyzed `main` commit in `prepared_from`; the merge must have that SHA as its first parent. If `main` advances, preparation must run again before merge. Merging the current release PR starts the release coordinator from protected `main`. It selects the exact merge commit, waits for its required checks, builds the six archives, and prepares the notes, package plan, package compatibility evidence, and digests of all ten unsigned files before requesting approval. Signing adds the eleventh asset, the detached sidecar. Neither T3 Code nor Codex is required.

The independent `stable-release` approval authorizes signing and subsequent publication of that entire candidate, including its exact crate versions. After approval, the workflow checks that the candidate is unchanged, signs the record, creates or safely resumes its draft, verifies the downloaded assets on native platforms, publishes the draft, runs public installer and upgrade checks, and publishes missing crates in dependency order. Any failed prerequisite stops later promotion. A separate human draft-publication approval and a second crates.io approval are no longer required in this lane. Every new manual recovery run enters the candidate approval gate again; removing the registry reviewer must not create a crates-only bypass.

The coordinator remains in `crates-publication.yml` so existing crates.io Trusted Publisher bindings retain their workflow identity. `crates-io-release` remains the main-only OIDC environment. Its reviewer requirement is removed only after this implementation is reviewed, merged, and the candidate approval gate is verified. `stable-release` keeps independent review and self-review prevention. Environment changes are an explicit administrator setup step, not an implicit effect of merging code.

Approval binds source, reviewed notes, archive bytes, generated installers, and the package plan. Retries may skip an independently confirmed already-published package, but may not introduce a different version, source commit, asset, or note body. An ambiguous existing tag, release, or asset is a hard stop. Published assets and crate versions remain immutable.

We considered retaining separate signing, GitHub publication, and crates.io approvals. Those pauses review the same candidate repeatedly and impose coordination work on a small team. One approval is justified only because the workflow exposes the complete candidate beforehand and retains automatic verification before each irreversible publication step. Public smoke still occurs after GitHub publication, so a failed public check can leave a public release while blocking crates.io; recovery preserves the original bytes and may require a new patch release.

The [operator guide](../release-automation.md) defines setup, the routine flow, and recovery. The remaining standalone key check, draft verification, and public smoke workflows are diagnostic and manual recovery tools; they are not the normal release entrypoint.
