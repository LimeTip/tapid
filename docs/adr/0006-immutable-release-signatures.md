# Non-expiring signatures for immutable release records

Tapid publishes release records and signatures as immutable GitHub release assets. A 30-day signature expiry would eventually prevent installation of an unchanged valid release, and renewing it would require a separate mutable metadata service. We instead authenticate those immutable records with non-expiring Ed25519 signatures, retaining record and archive digests, future-creation rejection, fail-closed validation, and the client's existing local rollback floor.

The signature schema is `tapid-release-v1-immutable-signature`, with exactly `schema` and `created_at` claims. Consumers reject the former time-limited schema and expiry claims rather than silently discarding an expired authorization. This supersedes the unsigned-record decision in ADR 0004 for the first release-record rollout. Historical signed manifests selected by `--endpoint` keep their freshness requirements.

A valid signature authenticates a record, not the freshness of the provider's latest-release alias. Existing installations reject versions below their release floor or installed version; fresh installations lack that history. Key compromise still requires the documented trust-root recovery or rotation procedure. We do not operate a periodically renewed metadata service.

The single-file installers use Tapid's native Rust verifier instead of downloading a Python program. Release CI embeds all six built archive hashes in the generated installer assets. The installer authenticates and validates the fixed bootstrap archive before executing its verification command against the embedded production keyring. This preserves signature verification without requiring users to install a runtime or introducing another verifier implementation. Website installer endpoints select the generated assets from the latest release. The trust root for initial installation remains the HTTPS-delivered installer and its embedded pins.
