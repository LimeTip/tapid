Policy-aware package execution foundations for Tapid. Existing approval APIs bind an exact artifact digest to the SHA-256 hash of a normalized script.

`RunConfig::parse_toml` accepts checked-in `[run.defaults]` and `[run.scripts.<name>]` profiles. Profiles declare project-relative read/write grants, network access, environment-variable names, subprocess access, and optional resource limits. `/` is the sole portable path separator; backslashes are rejected on every host. Configuration is strict, denies unknown fields, and cannot disable required sandboxing.

The platform-neutral execution API validates requests and reports stable errors, termination states, and per-dimension containment evidence. ADR 0005 now distinguishes **Restricted** authority containment from **ManagedTree** lifecycle ownership. Restricted requires requested filesystem/network authority, explicit environment/PATH and descriptor hygiene, and descendant propagation before spawn, but may report best-effort cleanup. ManagedTree additionally requires race-free kernel- or VM-owned descendants, a complete cleanup/kill boundary, and configured tree-wide timeout, output, process-count, and memory semantics. The assurance selector and native implementations remain future work in this crate.

Backend identities use checked construction: name, version, and optional deprecation text must be non-empty, free of control characters (including NUL), and no longer than `MAX_BACKEND_IDENTITY_BYTES`. Support and post-execution receipts distinguish restrictions requested by policy, capabilities declared by the backend, capabilities observed by runtime probes, and restrictions actually enforced for the execution. Each state reports filesystem read, filesystem write, network, environment sanitization, subprocess restriction, descendant lifecycle, timeout, output, process-count, and memory dimensions independently. Receipts must also identify the mechanism, assurance level, enforcement scope, and limitation; best-effort lifecycle discovery cannot be represented as ManagedTree. Receipt fields and construction remain private, so external callers cannot manufacture enforcement claims.

`ExecutionRequestBuilder::executable_search_path` and `executable_search_paths` accept an ordered list of explicit executable-search directories. The request preserves that order for adapter-owned `PATH` construction and rejects exact duplicates rather than silently changing precedence. Before duplicate checks, every entry is independently bounded and checked for NUL and target-platform representation, then the complete list is serialized with the target platform's exact `std::env::join_paths` rules. Consequently Unix entries containing `:` are rejected; Windows entries containing `;` use the standard library's quoting behavior and entries containing `"` are rejected. Published limits bound the directory count, each directory in native units, and the cumulative serialized search path including separators and its terminating NUL. These checks run before any backend support probe. During generic preflight, every entry must be absolute, existing, canonical, and a directory; different spellings that resolve to the same canonical/platform-semantic directory are rejected deterministically. Callers may therefore include a canonical project `node_modules/.bin` followed by the canonical bin directory of the selected Node runtime. Each entry becomes a `BackendRuntime` read-only `DirectorySubtree` grant in the enforcement receipt. Search paths are visible only to private adapters; callers cannot supply `PATH` through the environment API.

`ExecutionRequest` carries only explicit caller environment values whose names are both valid and allowlisted by the selected policy. Private adapters receive the complete controlled child environment: those explicit entries plus one mandatory `PATH` serialized from the ordered executable-search directories. An empty search list means `PATH=` rather than ambient or default executable lookup. `MAX_ENVIRONMENT_BLOCK_UNITS` covers that complete block, counting every `name=value` entry terminator, `PATH=`, joined-path separators, and the final environment-block terminator exactly once. Published limits also bound the program, argument count, each argument, cumulative argv payload, project root, and each environment value. Lengths are measured in bytes on Unix and UTF-16 code units on Windows. Embedded NUL and values that the target platform cannot represent are rejected before support probing; Unix otherwise preserves non-UTF-8 program, argument, project-root, search-path, and environment bytes. On Windows, argv validation uses a conservative upper bound rather than exact serialization: it counts the quoted program, argument separators, surrounding argument quotes, the mandatory terminating NUL, and worst-case doubling for quote/backslash escaping. Backends must start from this controlled environment rather than inherit ambient variables.

The sandboxed `execute` path rejects `SandboxMode::Disabled` and validates containment evidence before its private backend seam can add runtime paths or spawn. Existing project grants are canonicalized and retain typed `ExactFile` or `DirectorySubtree` semantics. A missing read target is rejected. A missing write target is declared as a directory subtree; the adapter must securely materialize it, re-resolve it, and bind it before native sandbox installation, or return unsupported containment. Explicit backend runtime additions must be absolute, existing, canonical, and retain their file/directory kind.

Receipts expose each effective grant's path, access, declared kind, source, and binding evidence. `NativeObject` means the adapter holds and revalidates a native object handle/identity for setup; pathname equality alone never makes that claim. `CanonicalPath` means the adapter freshly re-resolved the path immediately before setup and is never equivalent to `NativeObject`. Canonical-path enforcement has a residual trusted-host assumption: a privileged or concurrently mutating host must not replace path components between revalidation and native sandbox installation. The generic layer binds the receipt's paths, access, kinds, sources, binding modes, enforcement dimensions, and configured limits to the exact private preflight and rejects mismatches. Outcome accounting checked-adds captured stdout and stderr byte lengths and requires their combined size to be no greater than the exact preflight `max_output_bytes`, when configured. `TimedOut`, `OutputLimitExceeded`, `ProcessLimitExceeded`, and `MemoryLimitExceeded` are accepted only when that exact preflight configured the corresponding limit. Existing fields do not yet establish Restricted or ManagedTree support.

No platform adapter is implemented in this crate yet, so `execute` fails closed before spawning a child and cannot produce an enforcement receipt. Planned directions are experimental Seatbelt/`sandbox-exec` for macOS 26 Restricted, Landlock/`no_new_privs`/seccomp with runtime capability detection for Linux Restricted, and AppContainer or LPAC plus a Job Object on Windows. Native macOS 26 ManagedTree is unsupported; Linux ManagedTree needs proven namespaces and cgroup delegation. None is current behavior. `SandboxMode::Disabled` exists only for a future distinct, noisy `--no-sandbox` CLI outcome for trusted interactive projects; it must not contain an enforcement receipt or be a silent fallback, and this crate does not implement that escape.
